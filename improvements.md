# Предложения по улучшению тренажёра effector

Цель: вырастить проект от «маленького тренажёра» до уровня полноценной разработки,
не теряя учебной ценности. Каждый пункт: **что → какой навык effector отрабатывает →
что трогать (файлы) → объём** (S ≈ 1 сессия, M ≈ 2–3, L ≈ неделя).

Текущее состояние: 2 страницы, фейковые API через `setTimeout` прямо в моделях,
валидация, gate-паттерн, EXERCISES.md (exercises/) с 34 задачами. Ниже — что добавить дальше.

## Этап 2. Уверенная работа с данными (главная сила effector)

### 2.1. Централизованный фейковый API ⭐ ✅ (2026-11-20, shared/fake-api.ts)
- Что: вынести все «серверы» из моделей в один модуль `src/shared/fake-api.ts`:
  БД в памяти (клиент, продукты, статусы), настраиваемые задержки и **детерминированные сбои**
  (напр. `FAIL_RULES = { "amount%7": true, "everyNthRequest": 5 }`). Модели зовут
  `fakeApi.getProducts()`, `fakeApi.sendClaim(payload)` — эффекты остаются в моделях,
  а «поведение сервера» — в одном месте.
- Навык: честное разделение «клиент/сервер»; все упражнения про ошибки/гонки/кэши
  начинают воспроизводиться по щелчку (включая задачу 3.5 автоповтор).
- Файлы: новый `src/shared/fake-api.ts`, правки `entities/*`, `features/*/common.ts`.
- Объём: M. **Приоритет №3** — фундамент для 2.2–2.5.

### 2.2. Глобальная обработка ошибок API
- Что: событие `apiFail` в fake-api (или `sample` по `fx.fail` в каждой модели) →
  стор `$apiErrors` (очередь) → тост-компонент в `shared/ui` с кнопкой «Повторить».
- Навык: `fail`-события, очередь событий в сторе, вынос «показу» из модели.
- Файлы: `shared/fake-api.ts`, `shared/ui/index.tsx`, App.
- Объём: S–M. Зависит от 2.1.

### 2.3. Оптимистичные обновления
- Что: в истории статусов кнопка «Сменить статус» сразу добавляет строку,
  при `fxLoadHistory.fail` — откат (старое значение в сторе-«теневом» снапшоте).
- Навык: паттерн «оптимизм + откат» — классика продакшена, делается чисто на сторах.
- Файлы: `src/features/status-history/model.ts` + ui.
- Объём: M. Зависит от 2.1.

### 2.4. Персист в localStorage
- Что: «Недавно выбранные продукты» (задача E3 плана), последняя форма,
  тема, счётчики — синхронизировать со `localStorage` (эффект-запись по смене стора).
- Навык: сторы как единый источник состояния, которым можно «дописывать» извне;
  восстановление состояния при загрузке (`restore` + initial из storage).
- Файлы: `entities/credit/model.ts`, `features/credit-form/model`, новый `shared/storage.ts`.
- Объём: M.

### 2.5. Кэширование и инвалидация
- Что: обобщить упр. 3.2: `$productsCache` + `invalidateProducts()` (вызвать
  `fxGetCreditProducts` при смене продукта/по кнопке «Обновить данные»).
- Навык: кэш — это просто стор + событие инвалидации; подготовка к реальным
  query-паттернам без сторонних библиотек.
- Файлы: `entities/credit/model.ts`.
- Объём: S.

### 2.6. Отмена и «последний запрос побеждает»
- Что: довести упр. 3.3 до конца: `AbortController` в fake-api + сброс
  предыдущего запроса в `sample` (source = новый запрос).
- Навык: отмена эффектов, защита от гонок в «серверном» слое.
- Файлы: `shared/fake-api.ts`, `features/credit-form/model`.
- Объём: M. Зависит от 2.1.

### 2.7. Пагинация в истории
- Что: fake-api отдаёт статусы порциями; «Показать ещё» (эвент + `sample`
  с накоплением в `$statuses`).
- Навык: агрегация результатов эффектов в сторе, `source` с несколькими входами.
- Файлы: `shared/fake-api.ts`, `features/status-history/*`.

## Антипаттерны — чего НЕ делать

1. **Не апгрейдить effector до v23** — весь тренажёр и его связь с
   web-credit-management построены на API v22 (`fx.pending`, gate-рендер null).
2. **Не переносить логику в компоненты** — «проще прямо в JSX» убивает смысл проекта.
3. **Не добавлять Redux/MobX/Zustand** «для сравнения» — размывает фокус.
4. **Не рвать слои** (`pages → features/widgets → entities → shared`).
5. **Не использовать `<XGate />` как обёртку контента** (v22: рендерит null).
6. **Не тянуть тяжёлый UI-кит** — свои 5 компонентов в `shared/ui` осознанно малы.
