# Суть: что такое state-manager (~10 минут)

Не уровень: задач, вопросов и тестов здесь нет. Пропустить можно — каждая
задача курса объясняет «почему» по ходу. Но если до старта захочется общая
картина «как устроен этот проект и зачем» — читай здесь.

## 1. Состояние — ресурс приложения, а не компонента

`useState` живёт в компоненте: размонтировали — исчез; соседний компонент его
не видит; логику нельзя проверить без React. Данные приложения (клиент,
продукты, форма, ошибки) живут дольше любого компонента и общие для многих.
State-manager выносит состояние и правила его изменения из компонента в
отдельные модули, которые живут всё приложение. В этом проекте — файлы
`model/`.

## 2. Одно направление: событие → стор → экран

```
пользователь → (событие) → логика → (обновление) → стор → (подписка) → экран
```

Ничто не пишет на экран «сбоку»: React рендерит сторы, а сторы меняются только
по событиям. Выгода — отладка: вдруг «не то» → смотрим, какой стор рендерит
экран → какое событие его меняет → что пошло не так. Цепочка причин одна,
вторых тайных путей нет.

## 3. Приложение — граф, а не цепочка вызовов

Главная идея effector. Не думай «хэндлер вызывает функцию, которая вызывает
другую». Думай о **связях между юнитами**: события, сторы и эффекты — узлы,
`sample` и `combine` — рёбра. Ты описываешь *что зависит от чего*, а effector
сам это исполняет:

```ts
// «когда продукт выбран и сумма изменилась — пересчитать»
sample({ source: $amount, clock: $selectedProduct, fn: ... })
```

Чем больше приложение, тем сильнее окупается: логика не закопана в хэндлерах
в `.tsx`, а лежит на карте связей, которую можно прочитать и протестировать
без React.

## 4. Один источник истины — выводить, а не копировать

Одни и те же данные не живут в двух местах. Нужное собирают из уже существующих
сторов: `combine($a, $b)` или селектор `$x.map(...)`. Производный стор всегда
в синхроне — негде «забыть обновить копию».

## 5. Эффект — окно в внешний мир

Всё асинхронное (API, таймеры) — через `createEffect`. У эффекта есть
`done` / `fail` / `pending` — события и стор о его состоянии. Логика
реагирует на них, а не на промисы: `.then()` не разбросан по коду, а сосредоточен
в одном месте — эффекте.

## 6. Компонент — глупый

Обязанность компонента — ровно две вещи: рендерить сторы (`useStore`) и
шлать события (`useUnit` / пропсы-колбэки). Без бизнес-условий, без fetch,
без расчётов. Если «чуть-чуть логики» понадобилось в компоненте — это сигнал,
что её место в `model/`.

## 7. Один граф — N копий (scope)

Модель — «чертёж»: `fork()` даёт изолированную копию всего графа со своими
значениями. Два применения: тесты (у каждого теста свой scope — тесты не
мешают друг другу) и многоэкземпличные виджеты (два gate на одну модель —
две независимые копии). В курсе — уровень 5.

---

Всё, это и есть идеология. Остальное — API-синтаксис — учится импирекой:
задача → попробуй → проверь → (застрял) посмотри решение.
