# Самопроверка

Ответь без подсказок (и только потом сверься с кодом проекта).

1. Можно ли `$errors` вычислить в компоненте через `useMemo`? Технически — да.
   Чем это плохо по сравнению со стором?
2. Чем `sample({ clock })` отличается от `sample({ source })`? Что приходит
   в `fn` в каждом случае?
3. Почему `$selectedProduct` строится через `combine`, а не `map`?
4. Что произойдёт, если `changeAmount` вызывать из `useEffect` при каждом рендере,
   а не из `onChange`? (Подсказка: `$payload` → `fxRefreshSchedule` → …)
5. Зачем в `filter` писать тип-предикат `(p): p is SendClaimPayload`?
   Что сломалось бы в TypeScript без него?
6. В чём разница `$scheduleLoading` и `$schedule === null`? Приведи ситуацию,
   когда они **не совпадают** по смыслу.
7. Зачем нужен gate, если модель в этом проекте всё равно «живёт всегда»?
   Где в модели используются события gate?
8. Почему `$sending = fxSendClaim.pending` надёжнее, чем свой стор
   `$sending.on(sendClaim, () => true).on(fxSendClaim.done, () => false)`?
   (Подсказка: а что с `fail`?)
9. `$payload` объявлен как `const` без `export`. Почему это осознанное решение?
10. Когда нужен `attach({ effect })`, а когда достаточно `createEffect`?
    Приведи пример каждого из **этого** проекта.

<details>
<summary>Короткие опорные ответы</summary>

1. Стор живёт вне React: его читают виджеты и тесты, он пересчитывается
   реактивно без «эффектов», а логика валидации проверяется без рендера.
2. `clock` — «когда» (событие/изменение стора; в `fn` приходит payload/значение),
   `source` — «что взять» (значение стора или результат эффекта, передаётся в `fn`).
   Без `source` `fn` получает только значение clock.
3. Выбранный продукт зависит от **двух** единиц: списка и id. `map` видит одну.
4. Замкнутый цикл: рендер → эффект → событие → изменение стора → перерендер → …
   Плюс каждый «пересчёт» запускает «запрос» (дебаунс из 3.4 тут не спасёт —
   событие вызывается бесконечно, пока значение меняется).
5. TypeScript не умеет сам сузить `SendClaimPayload | null` до `SendClaimPayload`
   для пейлоада эффекта; предикат говорит: «после фильтра значение точно не null».
6. `loading` — «запрос в полёте»; `null` — «результата ещё не было никогда».
   Ситуация: продукт не выбран → `$payload` null → запроса нет → `loading` false,
   но `$schedule` тоже null (и это — «не готово», а не «загружается»).
7. Gate — договор «компонент на экране»: по нему модели грузят данные
   (`sample({ clock: XGate.open, … })`). В v22 страница рендерит сам компонент,
   а `<XGate />` в JSX — no-op (рендерит null).
   В original модель вообще **создаётся** при open (см. 5.5).
8. `.pending` сам обрабатывает и `done`, и `fail`, и повторные вызовы;
   ручная схема «забыла сброс на fail» — классический висячий индикатор.
9. Плат-лоад — внутреннее устройство модели. Публичный API фичи — это `$amount`,
   `$term`, `$errors`, `sendClaim` и т.п. То, что нельзя экспортировать,
   нельзя случайно «подключить» снаружи.
10. `createEffect` — для новых «голых» операций (`fxGetCreditProducts`,
    `fxSendClaimApi`). `attach({ effect })` — когда обработка уже есть в API-слое
    или чужом модуле, а модельу нужны **свои** `done`/`fail`/`pending`
    (`fxRefreshSchedule`, `fxSendClaim`, `fxCheckPromo`).

</details>

# Что дальше

Когда все 34 задачи позади:

1. **Вернись в оригинал** (реальный корпоративный проект) и найди реальные аналоги:
   `features/early-loan-repayment` (gate + модель), `entities/account`
   (`$accountOptions` из данных другого приложения), `shared/api`
   (эффекты поверх OpenAPI-клиента), `widgets/*` (виджеты-потребители).
2. Попробуй сделать в этом тренажёре то, чего ещё нет:
   - «история заявок» (несколько отправленных, стор массива + restore);
   - оптимистичное обновление: `sendClaim` сразу добавляет заявку в историю,
     при `fail` — убирает (подсказка: `.on(fxSendClaim.done/fail)` на одном сторе);
   - `$claimsCount`-бейдж на пункте меню «Заявка» (стор из фичи, читаемый в `app/`).
3. Прочитай доки: [effector.dev](https://effector.dev) — разделы `sample`,
   `combine`, `attach`, `Gate`, «Глобальные эффекты» и «Scope».
